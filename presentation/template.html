Exhibit 01 — The Complaint

The Problem

Every failed test opens the same cold case.

A test goes red. Now someone has to read the logs, the stack trace, the API response, maybe a screenshot — and decide, from scratch, what actually happened.

— Is this a real application defect, or just a flaky test?

— Is it a broken locator, an environment blip, or a config issue?

— Has this exact failure happened before?

— Is it severe enough to block the release?

That triage gets repeated by hand, from zero, every single time — and it's the same investigation whether it takes five minutes or an hour.

Exhibit 02 — The Method

The Solution

Three steps. No guessing.

01

Test Fails

Logs, stack trace, API response, expected vs. actual — submitted as-is.

02

AI Investigates

Classifies the failure, scores its own confidence, and cites which evidence led there.

03

QA Gets The Answer

Root cause, a Jira-ready defect, regression tests, and a release-risk verdict.

"AI identifies the most probable root cause based on available evidence" — never a guarantee. That line is enforced in code, not just copy.

Exhibit 05 — The Twist

The Differentiator

API says SUCCESS. UI times out.
Who's guilty?

A checkout order finishes successfully on the backend — but the automation can't find the confirmation banner. Most tools see "test failed" and stop there.

✕ The naive read

"Application Defect"

Test failed → file a bug against checkout. Wrong: it blames a working payment flow for a broken selector.

✓ AI QA Detective's verdict

Test Automation Issue

The API response is checked first — orderStatus: CONFIRMED, paymentStatus: SUCCESS. The failure is isolated to the automation's locator, not the app.

api response
{ "orderId": "ORD-88213", "orderStatus": "CONFIRMED", "paymentStatus": "SUCCESS" }
playwright
TimeoutError: .order-confirmation-banner
— locator resolved to 0 elements
— timeout exceeded
